The idea in plain language

A research desk feeding a claims calculator.

Think of PP as protection against a price move in the covered direction. Before selling it, we ask: “In situations like this, how often did we pay out, and how large were those payments?”

01

Find comparable situations

Use recent price swings, momentum, trading activity and the contract’s duration to find similar moments in the market’s past.

02

Research and challenge the news

A researcher classifies the event. A reviewer checks the source, timing and relevance. Old stories and unsupported claims are rejected.

03

Price possible payouts

Replay past price paths, allow for customers closing early, and estimate claims. Add the same profit and tail-risk allowance across every tested version.

The language model does not guess the premium. It supplies structured context. The numerical model controls probabilities and prices. When there are few comparable events, the news adjustment stays small.

In this study, research and verification are recorded assistant classifications that can be replayed offline. External API agents were not run: no API credentials were configured. The package includes a separate two-call research workflow for a future live test. This is not an independent-agent accuracy benchmark.

The payout error score is CRPS: it judges the whole predicted range of claims, in USDC per order. Gross profit assumes unchanged orders. Research plus review also changes how strongly sparse evidence is weighted, so their separate effects are not isolated here.

What “better” means here

Verified research adds 37.64 USDC over market-only pricing and slightly lowers the payout error score. The uncertainty range crosses zero, so a reliable advantage is not established.

Keyword rules and one research pass are almost identical in this sample. More complicated research is not automatically more predictive.

Base price and actual price differ

On the same 2,559 matched July orders, raw API Base premiums imply -31,428 USDC gross profit; actual paid prices imply 4,285 USDC.

Actual prices contain additional pricing components. Comparing only with the raw base would overstate the business improvement. Fixed-order model profit is 7,656 USDC on this same subset.

Customer behaviour changes the conclusion.

These are sensitivity scenarios, not measured demand forecasts. Higher-priced quotes may lose buyers; lower-priced quotes do not assume new customers appear.

The flat-price check matters. Applying the same overall 3.13% increase to every actual premium gives the same profit when orders are unchanged. Under moderate price sensitivity, that simple adjustment earns 7,198 USDC versus -1,639 for the model. The test has not demonstrated superior commercial allocation of prices.
What the experiment uncovered

Two limitations deserve attention.

Predicted claims / actual claims
64.0%

The model expects 66,245 USDC in July payouts; actual payouts total 103,434 USDC. The tail allowance lifts prices, but does not fix this underprediction.

This suggests a need to investigate contract-to-market alignment, jump risk and early exercise before deployment. A cause has not been established. The model still loses about 4,732 USDC on its worst July day.

Extra research cost the observed uplift could cover
0.015 USDC

Per July order, using the fixed-order point estimate. That is about 1.5 US cents before allowing for uncertainty.

At 0.02 USDC extra research cost per order, the observed event uplift becomes a net loss. Real API and research costs were not measured in this offline replay.

One useful source-check example: a Drift update is titled “June 3” but shows a June 4 publication date. Another recovery page includes later edits. The workflow records these clocks and rejects them as fresh broad Bitcoin shocks instead of treating every security-related headline as new danger.

What cannot be scored

All later payouts and paid premiums are hidden. We cannot calculate later profit, forecast accuracy or superiority from this file.

The file does contain closing times despite its dictionary saying otherwise. The implementation deliberately excludes them from quote inputs. It also excludes markup and API Base from model features.

A separate strict “actually received at the time” replay activates zero historical event signals because these sources were collected in October. The headline experiment uses disclosed publication-time proxies and is therefore not evidence of a live historical trading system.

How to use this work next

Ready for a stronger test, not live pricing.

  1. Collect news before the next quote.Store source publication, first arrival, processing time and revisions. Keep the original evidence and a stable event ID.
  2. Run the researcher and reviewer.Classify the event, verify the evidence, and cache the result. Use the numerical calculator for each contract; do not call an LLM to guess a price.
  3. Run shadow quotes alongside current prices.Use fresh candles, wait for real settlements, and keep prices unchanged while collecting evidence. Log offered prices and accept/reject behaviour for a later demand study.
  4. Evaluate under a new, fixed protocol.Collect at least 90 days and 50 distinct event episodes as an initial evidence target, not a guarantee of statistical power. Compare with market-only and simple rules at the same price policy, after measured costs.
  5. Promote only if the evidence clears the gates.Seek a positive cost-adjusted improvement with an uncertainty interval above zero, sound payout calibration, acceptable tail losses and commercially viable demand. Otherwise revise the hypothesis and test again.
